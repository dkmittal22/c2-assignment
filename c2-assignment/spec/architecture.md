# Architecture Specification

## 1. Purpose

Define the system structure, technology choices, and layer responsibilities for the Support Ticket Management System.

## 2. System Overview

The system is a modular monolith with two deployable parts:

1. **Backend API** — Spring Boot REST service with PostgreSQL
2. **Frontend SPA** — React application built with Vite

```
┌─────────────────┐     HTTP/JSON      ┌──────────────────┐
│  React (Vite)   │ ─────────────────► │  Spring Boot API │
│  localhost:5173 │ ◄───────────────── │  /api/v1/**      │
└─────────────────┘                    └────────┬─────────┘
                                                │
                                                ▼
                                       ┌──────────────────┐
                                       │   PostgreSQL     │
                                       │   (Flyway)       │
                                       └──────────────────┘
```

## 3. Technology Stack

| Concern | Choice |
|---------|--------|
| Language (backend) | Java 21 |
| Framework | Spring Boot |
| Persistence | Spring Data JPA |
| Database | PostgreSQL |
| Migrations | Flyway (sole schema owner) |
| Hibernate DDL | `spring.jpa.hibernate.ddl-auto=validate` |
| Build (backend) | Maven |
| API style | REST, JSON, base path `/api/v1` |
| Frontend | React + Vite |
| Local frontend origin | `http://localhost:5173` |
| Unit tests | JUnit 5, Mockito where isolation helps |
| Integration tests | Spring Boot Test + Testcontainers (PostgreSQL) |

## 4. Backend Layered Architecture

```
Controller
    ↓
Service (domain / business rules)
    ↓
Repository
    ↓
Database
```

### 4.1 Controller layer

Responsibilities:

- Map HTTP requests/responses
- Bind and trigger bean validation on request DTOs
- Reject unknown JSON fields (HTTP 400 `BAD_REQUEST`)
- Map malformed UUID path parameters to HTTP 400 `BAD_REQUEST`
- Delegate to services
- Return appropriate HTTP status codes

Must not:

- Contain business rules (including state-machine logic)
- Access repositories directly when business logic is required
- Expose JPA entities

### 4.2 Service layer

Responsibilities:

- Enforce ticket validation beyond transport-level checks where needed
- Enforce state-machine transitions
- Generate application UUIDs for new tickets and comments
- Orchestrate persistence operations
- Update `updatedAt` on ticket mutations
- Map between entities and DTOs (via dedicated mappers when used)

Must:

- Reject invalid transitions with HTTP 409 `INVALID_TRANSITION` at the API boundary
- Never rely on frontend validation

Must not:

- Introduce `@Version` or optimistic locking in v1

### 4.3 Repository layer

Responsibilities:

- CRUD and query access via Spring Data JPA against tables `tickets` and `comments`
- Pagination and case-insensitive substring search/filter queries for tickets

Must not:

- Contain business transition rules

### 4.4 Database

- PostgreSQL is the system of record
- Flyway is solely responsible for schema creation and evolution
- Application uses `spring.jpa.hibernate.ddl-auto=validate`
- IDs are generated by the application; PostgreSQL does not generate IDs
- Physical table names are fixed: `tickets`, `comments`

## 5. DTO Boundary Rule

- Request and response bodies use DTOs (Java records preferred where immutable DTOs are appropriate).
- JPA entities are persistence-only and must not be returned from controllers.
- Enums are used for finite domain values: `Priority`, `TicketStatus`.
- Unknown JSON properties on request DTOs are rejected.

## 6. Error Handling Architecture

- Centralized exception handling maps:
  - field validation failures → HTTP 400 `VALIDATION_ERROR`
  - illegal/unknown fields, malformed UUID, empty PATCH, `status` on create/PATCH → HTTP 400 `BAD_REQUEST`
  - valid UUID with no ticket → HTTP 404 `NOT_FOUND`
  - invalid transitions → HTTP 409 `INVALID_TRANSITION`
  - unexpected failures → HTTP 500 `INTERNAL_ERROR`
- Error body shape is defined in `spec/api-contract.md`.

## 7. Frontend Architecture

### Structure (logical)

| Area | Responsibility |
|------|----------------|
| Routes | `/tickets`, `/tickets/new`, `/tickets/{id}`; `/` redirects to `/tickets` |
| API client | Calls backend `/api/v1` endpoints; local origin `http://localhost:5173` |
| Forms | Create/edit ticket, add comment, transition |
| Error display | Surfacing `message` and `fieldErrors` from API |

### Response handling

| Operation | UI state update |
|-----------|-----------------|
| PATCH ticket | Replace local ticket fields from the PATCH response |
| Transition | Replace local ticket fields from the transition response |
| Add comment | Append the returned `CommentResponse` to local comments |

### Rules

- Frontend may restrict transition options to valid targets for UX.
- Frontend validation is optional convenience only.
- Backend remains the source of truth for all business rules.
- Search is submitted explicitly (Enter or button). No debounce requirement.

## 8. Configuration and Security (v1)

| Topic | Decision |
|-------|----------|
| Authentication | Out of scope — APIs are unauthenticated |
| Authorization | Out of scope |
| Secrets | Database credentials via environment / external config |
| Input validation | All external input validated on the backend |
| CORS | Allow `http://localhost:5173` for `/api/v1/**` |
| Logging | Do not log unnecessarily sensitive data |

## 9. Important Decisions

| Decision | Rationale |
|----------|-----------|
| Status changes only via transitions endpoint | Keeps lifecycle rules in one place; PATCH cannot bypass the state machine |
| No audit history table in v1 | Explicitly out of scope; only current status is stored |
| Assignee and comment author are free-text strings | No user entity exists without auth |
| Comments allowed on terminal tickets | Allows follow-up notes without reopening |
| Application-generated UUIDs | Explicit ID ownership; DB does not generate IDs |
| `ddl-auto=validate` + Flyway | Schema owned by migrations; Hibernate verifies mapping |
| No `@Version` in v1 | Concurrency control explicitly out of scope |
| Testcontainers PostgreSQL | Same engine as production |
| Case-insensitive substring search only | No full-text / Elasticsearch in v1 |

## 10. Non-Goals of This Architecture

- Service-to-service decomposition
- Message queues / event streaming
- Shared libraries beyond this application
- API gateway
- Optimistic locking
- Full-text search infrastructure
